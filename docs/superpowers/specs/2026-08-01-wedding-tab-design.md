# 결혼 준비 탭 설계 (2026-08-01)

## 목적

결혼 준비 중인 두 사용자가 준비 과정의 돈·할 일·업체·하객을 한 곳에서 공유 관리한다.
기존 가계부(월별 거래·통계·예산)와 **완전히 분리된 장부**로 동작한다 — 결혼 비용이
월별 통계와 누적 잔액을 왜곡하지 않는다.

## 확정된 요구사항 (사용자 Q&A)

- 탭 내용: **예산·지출 관리 + 체크리스트·일정 + 업체·견적 비교 + 하객·축의금 관리** (4가지 모두)
- 데이터 구조: **분리형** — 기존 `transactions`와 연동하지 않음
- 예산 항목마다 **부담 주체**(나/상대/공동)를 지정하고 사람별 부담 합계를 요약 표시
- 체크리스트는 **표준 템플릿**(한국 결혼 준비 순서)을 버튼으로 불러오고 자유 편집
- 구조: **결혼 탭 하나 + 내부 세그먼트 전환** (예산 | 체크리스트 | 업체 | 하객)

## 데이터 모델 (Firestore)

### `settings/wedding` — 단일 설정 문서
```
{ date: "2027-05-22", totalBudget: 50000000 }   // totalBudget은 선택(null 허용)
```

### `wedding_items` — 예산 항목 (문서 1개 = 항목 1개)
```
{
  name: "예식장",
  category: "venue",           // WEDDING_CATEGORIES 키 (constants.js)
  planned: 15000000,           // 계획 금액
  payer: "<이메일>" | "both",  // 부담 주체 — 표시는 ownerName() 재활용
  payments: [                  // 실결제 기록
    { label: "계약금", amount: 3000000, date: "2026-09-01" }
  ],
  memo: "",
  order: 3,
  vendorId: null               // 확정 업체 문서 ID (업체 세그먼트에서 연결)
}
```
- 지출액은 `payments` 합계로 파생한다. 별도 저장 금지(불일치 원천 차단).

### `wedding_tasks` — 체크리스트 (문서 1개 = 할 일 1개)
```
{ title: "상견례", period: "d12_9", done: false, memo: "", order: 1 }
```
- `period`는 시기 그룹 키. 그룹 라벨·순서는 `WEDDING_PERIODS` 상수(constants.js).
- 표준 템플릿 불러오기는 문서 ID `tpl_<n>` 고정 + `setDoc` → 두 명이 동시에 눌러도
  중복 없음(고정비 구체화와 같은 멱등 전략). 자동 시딩하지 않고 빈 상태 버튼으로만.

### `wedding_vendors` — 업체 후보
```
{ category: "venue", name: "○○웨딩홀", price: 15000000, contact: "", memo: "",
  status: "candidate" | "chosen" }
```

### `wedding_guests` — 하객
```
{ name: "김철수", side: "<이메일>", relation: "가족|친척|친구|직장|기타",
  count: 2, gift: 100000, memo: "" }
```
- `side`는 **둘 중 누구 측 하객인지**를 그 사람의 이메일로 저장한다(입력자와 무관한
  절대 기준 — 두 기기에서 동일하게 보인다). 표시 라벨은 `ownerName()`으로
  "<이름>측"처럼 만든다.
- 예상 인원 = `count` 합계, 축의금 합계 = `gift` 합계.

### 규칙·상태 관리
- `firestore.rules`에 `wedding_items`, `wedding_tasks`, `wedding_vendors`, `wedding_guests`
  match 블록 추가(모두 `isAllowed()`). 콘솔 재게시 필요 — README 절차에 명시.
- 결혼 데이터는 `loadAllData()`에 포함하지 **않는다**. 탭 최초 진입 시 한 번 로드하고
  (모듈 변수 플래그), 변경 후에만 해당 fetch를 다시 호출한다.
- rules 미게시 상태에서도 앱이 죽지 않도록 fetch는 `budget_plans`처럼 오류를 삼키고
  뷰에 안내 문구를 보여준다.

## 화면 구성 (토스 스타일)

### 내비게이션
- 사이드바와 모바일 하단 탭에 "결혼" 메뉴 1개 추가. 모바일 탭 grid는 7칸으로 확장.
- 뷰 컨테이너 `#view-wedding`, `js/views/wedding.js`가 `renderWeddingView()` export.
- 현재 세그먼트는 모듈 변수로 유지(재렌더·뷰 전환 생존).

### 공통 헤더 카드 (탭 상단 고정)
- D-day 히어로: `D-247 · 2027년 5월 22일 (토)`. 날짜 미설정이면 "결혼식 날짜를
  설정해주세요" 빈 상태 → 클릭 시 설정 모달(날짜 + 총예산). D-day 이후는 `D+n 🎉`.
- 총예산 진행 바: 전체 지출 합 / totalBudget (80% 경고색, 초과 시 빨강 — 기존 예산 카드 규칙).
  totalBudget 미설정이면 진행 바 대신 지출 합계만.
- 사람별 부담 요약: 나/상대/공동별 지출 합 (fmtMoneyShort 만/억 표기).

### 세그먼트별 화면
- **예산**: 항목 리스트(카테고리 색 점, 항목명, payer 태그, `지출/계획` + 미니 진행바).
  항목 클릭 → 모달: 이름·카테고리·계획액·부담 주체·메모 수정 + 결제 내역
  추가/삭제(계약금·중도금·잔금 라벨 프리셋 버튼 + 자유 입력). "항목 추가" 버튼은
  고정비 뷰의 대시 버튼 스타일.
- **체크리스트**: 상단 전체 진행률 바. `WEDDING_PERIODS` 순서로 시기 그룹 렌더,
  체크 시 취소선. 항목 추가/수정/삭제. 빈 상태에 "표준 체크리스트 불러오기" 버튼.
- **업체**: 카테고리 필터 칩 + 업체 카드(이름·가격·연락처·메모·상태 태그).
  "확정" → showConfirm으로 같은 카테고리 예산 항목에 견적가(planned)와 vendorId를
  반영할지 확인. 해당 카테고리 예산 항목이 없으면 새로 만들지 물어본다.
- **하객**: 요약 카드(총 인원, 측별 인원, 축의금 합계) + 명단 리스트. 측 필터 칩.

### 스타일 규칙
- 색은 전부 CSS 토큰. `WEDDING_CATEGORIES` 색은 카테고리 색과 같은 '데이터 색'으로
  constants.js에만 정의.
- 모든 클릭형 행/카드는 `role="button" tabindex="0"` 컨벤션 준수.
- 모달은 기존 `.modal-overlay` 재사용(모바일 바텀시트·Esc 닫기 자동 적용).
- 쓰기는 전부 try/catch + 성공 후 모달 닫기 컨벤션.

## 동작·엣지

- 동시 편집: 문서 단위 CRUD라 충돌 최소. 예외는 한 항목의 `payments` 배열
  (마지막 저장 승리) — 허용된 트레이드오프로 기록.
- 하객·축의금은 결혼식 후 정산 용도로 계속 사용 가능.
- 결혼 탭 데이터가 없거나 로드 실패 시에도 다른 뷰는 정상 동작.

## 단계 출시 (각 단계 완료 시 main 머지·배포)

1. 탭 신설 + 설정 모달(날짜·총예산) + 예산 세그먼트 (헤더 카드 포함)
2. 체크리스트 세그먼트 (+표준 템플릿)
3. 업체 세그먼트 (+확정 → 예산 연결)
4. 하객·축의금 세그먼트

## 범위 제외 (YAGNI)

- 예산 항목 드래그 정렬(등록순으로 충분, 필요 시 추후)
- 하객 참석 여부 체크(count로 식수 계산 충분)
- 기존 가계부 거래와의 연동/반영 옵션(분리형 확정)
- 실시간 동기화(onSnapshot) — 앱 전체가 폴링 방식이므로 일관성 유지
